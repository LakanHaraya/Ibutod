## Layunin

Isaayos ang naming ng mga counting method ng `Salalayan` upang maging mas malinaw ang kanilang layunin at upang maihiwalay ang **pagbibilang ng structural state** mula sa iba pang uri ng introspection. Layunin ding patunayan na nananatiling tama ang accounting invariants ng `Salalayan` matapos ang API refinement.

---

## Sinubukan

### Eksperimento Dalawampu (X20) — Paglilinaw ng Counting API

Pinalitan ang dating maiikling counting method:

| Dating API   | Bagong API        |
| ------------ | ----------------- |
| `used()`     | `countOccupied()` |
| `free()`     | `countFree()`     |
| `enabled()`  | `countEnabled()`  |
| `disabled()` | `countDisabled()` |

Nanatiling hindi nagbabago ang mga structural introspection method:

```cpp
capacity()
isEmpty()
isFull()
```

Sinubukan ang bagong API sa iba't ibang structural states ng isang `Salalayan<4>`.

### Initial State

Sinuri ang accounting ng isang bagong likhang `Salalayan`.

Inasahang resulta:

```txt
Capacity: 4
Occupied: 0
Free: 4
Enabled: 0
Disabled: 4
```

Lahat ng pagsusuri ay nagresulta sa `PASS`.

---

### Occupancy Counting

Nag-attach ng tatlong `Sapad` sa apat na `Salpakan`.

```txt
#1 → IMU
#2 → GNSS
#3 → Telemetry
#4 → Free
```

Pinatunayan:

```txt
Occupied == 3
Free == 1
```

Kasama ang invariant:

```txt
Occupied + Free == Capacity
```

---

### Enablement Counting

Nag-enable ng dalawang occupied na `Salpakan`.

```txt
#1 → Enabled
#2 → Disabled
#3 → Enabled
#4 → Disabled
```

Pinatunayan:

```txt
Enabled == 2
Disabled == 2
```

Kasama ang invariant:

```txt
Enabled + Disabled == Capacity
```

Sinuri rin ang structural constraint:

```txt
Enabled <= Occupied
```

---

### Independent Counting Dimensions

Sinubukan ang pagkakaiba ng occupancy at enablement.

Halimbawa:

```txt
Occupied: 3
Enabled: 2
```

Pinatunayan na ang dalawang ito ay hindi magkaparehong konsepto.

Ang isang `Salpakan` ay maaaring:

```txt
Occupied + Disabled
```

Samantalang hindi maaaring magkaroon ng enabled `Salpakan` na walang nakakabit na `Sapad`.

---

### Counting After State Changes

Sinubukan ang accounting matapos ang pagbabago ng structural state.

Isinagawa:

```txt
Disable #1
Detach Sapad from #1
```

Matapos ang pagbabago:

```txt
Occupied: 3
Free: 1
Enabled: 1
Disabled: 3
```

Muling pinatunayan ang mga accounting invariant.

Lahat ng pangunahing pagsusuri ay nagresulta sa `PASS`.

---

## Mga Natuklasan

### 1. Mas Malinaw na Semantic Intent

Ang prefix na `count` ay naglilinaw na ang mga sumusunod ay mga aggregation operation:

```cpp
countOccupied()
countFree()
countEnabled()
countDisabled()
```

Hindi lamang sila state query kundi aktuwal na pagbibilang ng mga `Salpakan` batay sa kani-kanilang structural state.

---

### 2. Dalawang Independent Structural Dimensions

Nanatiling malinaw ang paghihiwalay ng:

```txt
Occupancy
```

at:

```txt
Enablement
```

Maaaring ilarawan ang isang `Salpakan` gamit ang dalawang dimension:

| Occupancy | Enablement | Halimbawa                     |
| --------- | ---------- | ----------------------------- |
| Free      | Disabled   | Walang nakakabit na Sapad     |
| Occupied  | Disabled   | Nakakabit ngunit hindi aktibo |
| Occupied  | Enabled    | Nakakabit at naka-enable      |

Ang counting API ay sumusukat sa bawat dimension nang hiwalay.

---

### 3. Accounting Invariants

Napatunayan ang sumusunod na structural invariants:

```txt
countOccupied() + countFree() == capacity()
```

at:

```txt
countEnabled() + countDisabled() == capacity()
```

Kasama rin ang kasalukuyang enablement boundary:

```txt
countEnabled() <= countOccupied()
```

Ang mga invariant na ito ay maaaring magsilbing mahalagang batayan sa mga susunod na lifecycle at diagnostics experiments.

---

### 4. Walang Behavioral Expansion

Ang `v0.1.20` ay hindi nagdagdag ng bagong runtime behavior.

Hindi binago ang:

* attachment behavior;
* detachment boundary;
* enablement behavior;
* `Sapad` abstraction;
* lifecycle behavior; o
* ownership model.

API refinement lamang ang isinagawa.

---

## Architectural Boundary

Hindi pa idinagdag sa bersiyong ito ang:

* bagong `Salpakan` lifecycle model;
* `Sapad` lifecycle contract;
* `Sapad` execution interface;
* ownership semantics;
* runtime replacement mechanism;
* hot-swapping behavior;
* `Silid` abstraction;
* scheduler;
* system-wide registry; o
* dynamic allocation.

Nanatiling structural at introspective ang saklaw ng pagbabago.

---

## Tala

Ang `v0.1.20` ay isang maliit ngunit mahalagang refinement release.

Sa halip na magdagdag agad ng panibagong abstraction, inayos muna ang semantic clarity ng kasalukuyang API. Ang pagbabago mula sa:

```cpp
used()
free()
enabled()
disabled()
```

patungo sa:

```cpp
countOccupied()
countFree()
countEnabled()
countDisabled()
```

ay naghahanda ng mas malinaw na vocabulary para sa mga susunod na pagtalakay tungkol sa structural state, lifecycle, diagnostics, at execution.

Mahalaga ring napatunayan sa eksperimentong ito na ang `Occupancy` at `Enablement` ay dalawang magkaibang structural dimension. Ang paghihiwalay na ito ay magiging mahalagang batayan sa susunod na architectural review ng lifecycle ng `Salpakan`.

Sa puntong ito, ang susunod na pangunahing tanong ay hindi pa tungkol sa pagdaragdag ng mas maraming class. Sa halip:

> **Ano ang wastong lifecycle ng isang Salpakan, at saan nagsisimula at nagtatapos ang lifecycle responsibility ng Sapad?**

Ito ang magiging susunod na mahalagang direksiyon ng pagpapaunlad ng Ibutod.
