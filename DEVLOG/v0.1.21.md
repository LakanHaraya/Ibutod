## Layunin

Suriin at linawin ang tunay na responsabilidad ng `Salpakan` sa loob ng kasalukuyang arkitektura ng Ibutod.

Sa mga naunang bersiyon, ang `Salpakan` ay naglalaman ng simpleng runtime lifecycle sa pamamagitan ng:

* `begin()`;
* `update()`;
* `state()`;
* `isReady()`; at
* `uptime()`.

Gayunpaman, walang malinaw na architectural justification kung bakit ang mismong structural attachment point ang dapat magkaroon ng sariling execution lifecycle.

Layunin ng bersiyong ito na alisin ang runtime lifecycle mula sa `Salpakan` at panatilihin lamang ang mga responsabilidad na malinaw na likas sa pagiging isang structural attachment point.

## Sinubukan

### Eksperimento Dalawampu't Isa (X21) — Paglilinis sa Estruktura ng Salpakan

Sinubukan ang `Salpakan` matapos alisin ang dating runtime lifecycle API.

Ang pagsusuri ay nakatuon sa pagpapatunay na nananatiling buo ang structural behavior ng `Salpakan` at `Salalayan`.

Sinubukan ang sumusunod:

* initial structural state;
* attachment ng mga `Sapad`;
* occupancy accounting;
* selective enablement;
* enablement boundary;
* detachment boundary;
* local structural identity; at
* out-of-range identity rejection.

Halimbawa ng structural composition:

```txt
Salalayan<4>
│
├── Salpakan #1 ── Sapad
├── Salpakan #2 ── Sapad
├── Salpakan #3 ── Sapad
└── Salpakan #4 ── Free
```

Sinubukan din ang sumusunod na structural transitions:

```txt
Free
 │
 │ attach(Sapad*)
 ▼
Occupied + Disabled
 │
 │ enable()
 ▼
Occupied + Enabled
 │
 │ disable()
 ▼
Occupied + Disabled
 │
 │ detach()
 ▼
Free
```

Ang lahat ng pangunahing pagsusuri ay nagresulta sa `PASS`.

## Mga Natuklasan

### 1. Hindi Kailangan ng Sariling Runtime Lifecycle ng Salpakan

Napatunayan na ang pangunahing structural responsibilities ng `Salpakan` ay nananatiling gumagana kahit walang:

```cpp
begin();
update();
state();
isReady();
uptime();
```

Ang mga ito ay hindi kinakailangan upang suportahan ang:

* identity;
* attachment;
* detachment;
* occupancy;
* enablement; at
* structural introspection.

Ipinapakita nito na ang runtime lifecycle ay isang hiwalay na concern mula sa structural state ng `Salpakan`.

---

### 2. Ang Salpakan ay Structural Attachment Point

Mas malinaw na ngayon ang papel ng `Salpakan`.

Ito ay:

* may lokal na identity;
* maaaring magkaroon ng pangalan;
* maaaring maging `Free` o `Occupied`;
* maaaring `Disabled` o `Enabled`;
* maaaring pagkabitan ng isang `Sapad`; at
* maaaring tanggalan ng nakakabit na `Sapad` sa ilalim ng itinakdang structural boundary.

Hindi nito awtomatikong ipinahihiwatig ang:

* initialization;
* execution;
* scheduling;
* runtime state machine; o
* ownership ng execution lifecycle.

---

### 3. Magkahiwalay ang Occupancy at Enablement

Nanatiling malinaw ang dalawang magkahiwalay na structural dimension:

```txt
Occupancy
├── Free
└── Occupied

Enablement
├── Disabled
└── Enabled
```

Ang isang `Salpakan` ay maaaring magkaroon ng nakakabit na `Sapad` ngunit nananatiling disabled.

```txt
Occupied + Disabled
```

Ang enablement ay hindi rin maaaring gamitin upang bigyang-kahulugan ang runtime execution ng nakakabit na `Sapad`.

Sa puntong ito, ang `Enabled` ay nangangahulugan lamang na ang mismong `Salpakan` ay pinahintulutang maging enabled sa structural model.

---

### 4. Nanatiling Buo ang Structural Boundaries

Matapos alisin ang lifecycle API, nanatiling gumagana ang sumusunod:

```cpp
salalayan.attach(id, sapad);
salalayan.detach(id);

salalayan.enable(id);
salalayan.disable(id);

salalayan.countOccupied();
salalayan.countFree();

salalayan.countEnabled();
salalayan.countDisabled();
```

Nananatili rin ang mga structural invariant:

```txt
Occupied + Free == Capacity

Enabled + Disabled == Capacity

Enabled <= Occupied
```

Ang mga invariant na ito ay hindi nangangailangan ng anumang runtime lifecycle state.

## Architectural Boundary

Hindi pa idinagdag o tinukoy sa bersiyong ito ang:

* `Sapad` execution lifecycle;
* `Sapad` initialization contract;
* `Sapad` update contract;
* runtime scheduler;
* execution order;
* callback mechanism;
* ownership model ng `Sapad`;
* dynamic `Sapad` replacement policy;
* automatic execution kapag na-enable ang `Salpakan`;
* global lifecycle manager;
* `Silid` class; o
* system-wide runtime orchestration.

Mahalaga ring tandaan na:

> Ang `enable()` ng `Salpakan` ay hindi nangangahulugang awtomatikong magsisimula ang execution ng nakakabit na `Sapad`.

Ang dalawang konseptong ito ay sadyang hindi pa pinagdurugtong.

---

## Tala

Ang `v0.1.21` ay isang pagbabawas ng functionality sa antas ng API, ngunit isang pagpapalinaw sa antas ng arkitektura.

Sa halip na magkaroon ang `Salpakan` ng parehong structural at runtime responsibilities, pinili na paghiwalayin muna ang mga ito.

Sa puntong ito, maaaring ilarawan ang kasalukuyang arkitektura bilang:

```txt
Ibutod
│
├── Salalayan
│   └── Structural grouping boundary
│
├── Salpakan
│   ├── Local identity
│   ├── Attachment point
│   ├── Occupancy
│   └── Enablement
│
└── Sapad
    └── Attachable object
        (execution behavior undefined)
```

Ang mahalagang natitirang architectural question ay hindi na kung paano magpapatakbo ang `Salpakan`, kundi:

> **Ano ang execution contract ng isang `Sapad`, at sino ang may pananagutan sa pagsisimula, pagpapatakbo, at paghinto nito?**

Hindi pa ito sinasagot sa `v0.1.21`.

Ang bersiyong ito ay nagsisilbing paghahanda upang pag-aralan ang lifecycle at execution model ng `Sapad` nang hindi ipinipilit ang mga responsibility na iyon sa `Salpakan`.
