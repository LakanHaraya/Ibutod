## Layunin

Magbigay ng minimal at malinaw na execution boundary para sa `Sapad` nang hindi ibinabalik ang runtime lifecycle sa `Salpakan`. Sa `v0.1.21`, inalis ang runtime lifecycle ng `Salpakan` upang linawin na ang `Salpakan` ay isang structural attachment point lamang. Dahil dito, nanatiling bukas ang isang mahalagang architectural question:

> **Kung ang `Salpakan` ay hindi responsable sa execution lifecycle, ano ang pinakamaliit na execution contract ng isang `Sapad`?**

Layunin ng bersiyong ito na subukan ang isang minimal na execution interface para sa `Sapad`.

Ang napiling contract ay:

```cpp
virtual void run() = 0;
```

Ang `run()` ay sadyang maliit at generic. Hindi nito ipinapalagay na ang `Sapad` ay isang scheduler task, periodic update function, callback, o RTOS task.

Ang `Sapad` ay itinuturing bilang isang modular na program unit na may tiyak na layunin at maaaring magkaroon ng sariling execution behavior.

---

## Sinubukan

### Eksperimento Dalawampu't Dalawa-A (X22-A) — Single Sapad Execution
Sinubukan ang pangunahing `Sapad::run()` execution contract gamit ang isang kongkretong `Sapad`. Napatunayang maaaring tawagin ang `run()` nang hiwalay sa `Salpakan` lifecycle.

### Eksperimento Dalawampu't Dalawa-B (X22-B) — Multiple Sapad Instances
Sinubukan ang dalawang magkahiwalay na `Sapad` instance. Napatunayang independent ang kanilang execution state.

### Eksperimento Dalawampu't Dalawa-C (X22-C) — Multiple Sapad Types
Sinubukan ang iba't ibang konkretong uri ng `Sapad`. Napatunayang nananatili ang sariling behavior ng bawat uri sa pamamagitan ng polymorphism.

### Eksperimento Dalawampu't Dalawa-D (X22-D) — Execution Through Salpakan
Sinubukan ang pagkuha ng `Sapad` sa pamamagitan ng `Salpakan::sapad()` at ang pagpapatakbo nito mula roon. Napatunayang hindi kinakailangang malaman ng `Salpakan` ang konkretong uri ng `Sapad`.

### Eksperimento Dalawampu't Dalawa-E (X22-E) — Detach at Reattach
Sinubukan ang detach at reattach ng `Sapad`. Nanatiling ipinagbabawal ang detach habang enabled ang `Salpakan`, at ang reattached `Sapad` ay nananatiling disabled hanggang sa tahasang i-enable.

### Eksperimento Dalawampu't Dalawa-F (X22-F) — Final Invariants
Isinagawa ang panghuling pagsusuri sa occupancy, enablement, attachment, detach/reattach, at `Sapad` execution. Lahat ng itinakdang invariant ay pumasa.

## Mga Natuklasan

### 1. Ang Sapad ay Maaaring Magkaroon ng Sariling Execution Contract

Napatunayan na hindi kinakailangang magkaroon ang `Salpakan` ng sariling runtime lifecycle upang magkaroon ng execution behavior ang nakakabit na `Sapad`.

Ang minimal na boundary:

```cpp
virtual void run() = 0;
```

ay sapat upang magbigay ng isang malinaw na interface para sa execution.

Hindi nito tinutukoy kung paano, kailan, o gaano kadalas tatakbo ang `Sapad`.

---

### 2. Ang `run()` ay Execution Contract, Hindi Scheduler

Ang `run()` ay isang execution entry point lamang.

Hindi nito ipinahihiwatig na ang `Sapad` ay:

* periodic task;
* scheduler-managed task;
* RTOS task;
* callback;
* infinite loop; o
* awtomatikong tumatakbo sa background.

Maaaring maikli o katamtaman ang isang `Sapad` at magkaroon ng tiyak na layunin. Ang aktuwal na behavior ng `run()` ay responsibilidad ng concrete `Sapad` implementation.

---

### 3. Nanatiling Polymorphic ang Sapad Boundary

Maaaring magkaroon ng magkakaibang concrete `Sapad` type sa iisang structural environment.

```txt
Sapad
├── SensorSapad
├── CounterSapad
└── iba pang concrete Sapad
```

Ang `Salpakan` ay hindi kailangang malaman ang kanilang konkretong uri.

Ang attachment boundary ay nananatiling:

```cpp
Sapad*
```

at ang execution boundary ay:

```cpp
run()
```

Ito ay nagbibigay ng maliit na abstraction boundary nang hindi nagdaragdag ng registry, factory, o dynamic dispatch management layer sa labas ng kinakailangang virtual dispatch ng C++.

---

### 4. Nanatiling Non-Owning ang Attachment

Ang `Salpakan` ay nag-iimbak lamang ng reference sa isang `Sapad`:

```cpp
Sapad* _sapad = nullptr;
```

Hindi nito inaangkin ang ownership ng object.

Ang lifecycle ng concrete `Sapad` object ay nananatiling responsibilidad ng application o caller.

Dahil dito, ang:

```cpp
detach()
```

ay nag-aalis lamang ng attachment reference.

Hindi nito:

* dine-delete ang `Sapad`;
* winawasak ang object;
* nire-release ang memory nito; o
* awtomatikong nire-recreate ang object sa reattach.

---

### 5. Nanatiling Magkahiwalay ang Occupancy, Enablement, at Execution

Sa kasalukuyang architecture, tatlong magkakaibang konsepto ang maaaring ilarawan:

```txt
Occupancy
├── Free
└── Occupied

Enablement
├── Disabled
└── Enabled

Execution
└── Sapad::run()
```

Hindi awtomatikong nagiging execution state ang enablement.

Halimbawa:

```txt
Occupied + Disabled
```

ay isang wastong structural state.

Ang `Sapad` ay maaari pa ring magkaroon ng `run()` execution contract kahit hindi awtomatikong nagbabago ang structural enablement nito.

---

### 6. Walang Automatic Execution sa Enablement

Hindi binago ng `v0.1.22` ang kahulugan ng:

```cpp
salalayan.enable(id);
```

Hindi ito awtomatikong nagsasagawa ng:

```cpp
sapad()->run();
```

Nanatiling magkahiwalay ang:

```txt
enable()
```

at:

```txt
run()
```

Ito ay sadyang pinanatili upang hindi maipilit ang isang execution policy bago pa ito maayos na mapag-aralan.

---

### 7. Napanatili ang Structural Invariants

Muling napatunayan ang:

```txt
countOccupied() + countFree() == capacity()
```

at:

```txt
countEnabled() + countDisabled() == capacity()
```

Kasama ang:

```txt
countEnabled() <= countOccupied()
```

Ang mga invariant na ito ay nanatiling tama kahit isinama na sa eksperimento ang attachment, enablement, execution, detach, at reattach behavior.

---

## Architectural Boundary

Hindi pa idinagdag o tinukoy sa bersiyong ito ang:

* `Sapad` scheduler;
* automatic execution mechanism;
* periodic execution;
* execution frequency;
* execution order;
* execution queue;
* callback mechanism;
* `Sapad` lifecycle;
* `Sapad` initialization contract;
* `Sapad` shutdown contract;
* ownership model;
* dynamic allocation;
* automatic `Sapad` replacement;
* hot-swapping policy;
* multithreading;
* RTOS integration;
* global execution registry;
* system-wide execution manager;
* `Silid` class; o
* automatic execution kapag nag-`enable()` ang `Salpakan`.

Nanatiling maliit ang execution boundary:

```txt
Salpakan
    │
    └── non-owning Sapad*
            │
            └── run()
```

Ang execution contract ay naidagdag sa `Sapad`, ngunit ang execution authority ay hindi pa itinatag sa antas ng `Salalayan`, `Salpakan`, o buong Ibutod system.

---

## Tala

Ang `v0.1.22` ay isang mahalagang pagpapatuloy ng structural purification na isinagawa sa `v0.1.21`.

Sa `v0.1.21`, inalis ang runtime lifecycle mula sa `Salpakan` upang maiwasan ang paghahalo ng structural responsibility at execution responsibility.

Sa bersiyong ito, sinubukan naman kung saan maaaring ilagay ang pinakamaliit na execution boundary.

Ang naging resulta ay:

```txt
Ibutod
│
├── Salalayan
│   └── Structural grouping boundary
│
├── Salpakan
│   ├── Local identity
│   ├── Attachment point
│   ├── Occupancy
│   └── Enablement
│
└── Sapad
    ├── Modular program unit
    └── Execution boundary
        └── run()
```

Ang paghihiwalay na ito ay mas malinaw kaysa sa dating modelo kung saan ang `Salpakan` mismo ay may `begin()` at `update()` lifecycle.

Sa kasalukuyan, ang `Sapad` ay may paraan upang magsagawa ng sariling execution behavior, ngunit wala pang tinukoy kung sino ang may awtoridad na magsabi kung **kailan** ito dapat tumakbo.

Mahalagang huwag munang lutasin ang tanong na iyon sa pamamagitan ng pagdaragdag agad ng scheduler o lifecycle manager.

Ang susunod na architectural question ay:

> **Sino ang may execution authority sa isang `Sapad`, at ano ang kaugnayan ng `Salpakan` enablement sa aktuwal na pagpapatakbo nito?**

Sa puntong ito, malinaw na ang `run()` ay isang execution contract lamang. Hindi pa ito execution policy.

Ang `v0.1.22` ay samakatuwid isang boundary-definition release: nagkaroon ang `Sapad` ng pinakamaliit na kinakailangang execution interface habang nananatiling simple, static, non-owning, at structural ang natitirang arkitektura ng Ibutod.
